Nurse avatar video-call demo

System description, 2026-10-22. A patient on a Mac video-calls an AI nurse: snow runs the conversation, and SoulX-FlashHead renders the nurse's face lip-synced to her voice on a cloud GPU.

~25 fpslive 512×512 avatar video, continuous for the whole call
1.5 smedian from the patient's final transcript to the reply's TTS
~2.2 sreply TTS start to the first avatar frame (H200, through the tunnel)
1.45×H200 render speed vs real time: headroom for live idle motion

1. What the demo does

  • The patient opens the demo page on the Mac and starts a VOIP call with the nurse agent ("Stacy", CHF discharge script).
  • Snow handles the conversation: voice activity detection, speech recognition, the agent (LLM plus safety engines), and TTS.
  • The nurse's TTS audio is streamed to a GPU server running FlashHead Pro, which turns a still image of the nurse (figures/nurse_image3.png) into talking-head video, frame by frame, in real time.
  • Each video frame travels back with its own 40 ms of audio, so the browser plays voice and lips in sync.
  • Between replies the GPU keeps rendering idle motion from silent audio (head sway, blinks), so the nurse never freezes or jumps.

2. Pipeline

Step by step

  1. Patient speaks. The page streams microphone audio to snow_call over the VOIP socket.
  2. VAD and ASR. Snow detects the end of the patient's turn and transcribes it with context-aware ASR v3.
  3. Agent. The LLM writes the reply, while safety engines (RedTeam, pause detection, date-of-birth verification and others) run alongside.
  4. TTS. ElevenLabs synthesizes the reply in pieces (often clauses), each arriving as a fast burst of audio.
  5. Forwarder. avatar_forwarder.py taps snow's outgoing agent audio, resamples it to 16 kHz, and streams it to the GPU server. A reply ends after 1.0 s with no new audio; a barge-in sends flush.
  6. Tunnel. The audio goes through an SSH tunnel (localhost:8767 → pod :8766) kept up by a watchdog.
  7. Render. The GPU server cuts the audio into 1.12 s chunks. FlashHead Pro renders 28 frames per chunk in about 0.77 s. Between replies it renders silence, which gives natural idle motion.
  8. Frames back. Each frame (JPEG, quality 70) is paired with its 40 ms of audio and sent at a steady 25 fps on the same link.
  9. Playback. snow_call relays each frame unchanged to the call's socket.io room. The page schedules the audio back to back and draws each frame exactly when its audio starts, so lips match the voice.

3. Timing of one turn

The avatar adds about 2.7 s to snow's usual turn latency: about 2.2 s to the first frame, plus the 0.5 s browser buffer. Snow's own (muted) playback of the agent voice is delayed by the same amount (avatar_delay_ms=2550), so snow's turn-taking follows what the patient actually hears.

5. Key design decisions

  • Audio travels inside the video frames. Every frame carries its own 40 ms of audio, and the browser draws a frame when its audio starts playing. Lip sync then survives any network jitter, because voice and video can't drift apart.
  • Snow's own voice stays on, but muted and delayed. Snow's turn-taking relies on playback acknowledgements from the browser, so its copy keeps playing silently, delayed to match the avatar. Without the delay, the nurse's voice leaking into the mic looked like barge-ins (18 VAD cancels in 2 minutes).
  • Live idle motion (H200 only). The GPU renders silence between replies, keeping about 1 s buffered. When a reply starts, only the next 0.25 s of idle is kept, so replies aren't delayed and motion stays continuous. Settings: AVATAR_IDLE_TARGET_S=1.0, AVATAR_IDLE_KEEP_S=0.25. The target must exceed the 0.77 s render time; 0.5 s ran dry at 21.8 fps.
  • A reply ends after 1.0 s without audio. TTS delivers a turn in bursts 0.5–0.7 s apart. A shorter gap split turns and padded silence mid-sentence.
  • One GPU client at a time. A new connection replaces the old one, and the forwarder ignores calls that have ended. A stale link once shared the frames, leaving each stream every other frame.
  • Graceful degradation. If the GPU link drops, the page unmutes snow's own voice and the call continues voice-only. The forwarder reconnects with backoff (0.5 to 5 s) and the tunnel watchdog reopens the tunnel.

7. Running it

  1. Mac, after any colima start: set the VM's default route through col0 and its MTU to 1280 (runbook.md step 0).
  2. Container: run start_services.sh (Postgres, Redis).
  3. GPU: check that yuntang-avatar-h200 is up and its server job is listening (sky … --config active_workspace=speech).
  4. Tunnel: ./gpu_tunnel.sh yuntang-avatar-h200, then a smoke test with demo/test_client.py (expect about 25 fps).
  5. Snow and UI: run ./start_snow.sh.
  6. Mac: open demo link 2 and click Start Call once.

Full details are in avatar_demo/docs/runbook.md in the SoulX-FlashHead fork. The network background is in network_and_frame_drops.md.

10. Known limits

  • Latency. The avatar adds about 2.7 s per turn, about 4 s from the patient's last word to the nurse's first word.
  • One call at a time. The GPU server holds one conversation session.
  • Network settings don't persist. The Colima route and MTU are lost on a Colima restart, unless the provision script in network_and_frame_drops.md is installed.
  • Live idle needs a fast GPU. It's an H200 feature. On 2× RTX the page falls back to the idle clip between replies.
  • Demo-only code. All of this is local and off by default. Nothing runs unless AVATAR_GPU_WS_URL is set and the page has ?avatar=1.

The reserved H200 node (gd942bc, cw-usw4) has a reservation label and taint. Remove both when the demo ends, using the two kubectl commands in the cluster config's header.
